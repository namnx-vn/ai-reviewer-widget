## Detection Contract
Model sinks centrally: command execution, database raw query APIs, template/evaluation APIs, response-header APIs, and other explicit interpreters. Vulnerability semantics requiring attacker control MUST prove `source → propagation → sink`; dangerous API presence alone is insufficient.

SQL handling must distinguish string interpolation/concatenation/raw query APIs from parameterized queries and known-safe ORM abstractions. No rule may implement a private taint engine.

## Implementation

Phase 3.6.2 implements all ten rule families using shared reusable primitives under `src/analyzer/security/flow/` and centrally modeled source/sink/sanitizer identities under `src/analyzer/security/rules/injection/`.

The current shared flow slice provides deterministic intraprocedural multi-label propagation for direct request sources, assignments, aliases, template literals, concatenation, logical/conditional expressions, common object/array propagation, basic branch flow, sink calls, and sink-aware sanitizers. Findings retain deterministic source/transform/sanitizer/sink evidence paths.

Modeled sinks include Node command execution, raw SQL query text, NoSQL query/operator objects, template source compilation/rendering, expression interpreters, response header name/value sinks, LDAP filters, XPath expressions, and GraphQL operation documents. Imported, namespace, default-import, CommonJS, and obvious callable alias identities are resolved for explicitly modeled libraries where supported.

SQL parameter values and GraphQL variable values are intentionally kept separate from query/document text so safe parameterization does not become a finding. Sanitizers are typed by sink family; a sanitizer for one injection class does not clear unrelated taint.

This implementation is intentionally the minimum shared intraprocedural taint slice required by 3.6.2. Phase 3.6.19 remains responsible for generalizing and expanding the reusable taint engine across security domains, propagation forms, performance/caching, and richer framework modeling. Phase 3.6.20 remains responsible for cross-function and cross-file propagation. These later phases MUST extend the shared flow boundary rather than introduce private rule-specific taint engines.

## Tests
For every family include direct taint, variable propagation, template literal, concatenation, constants, parameterization/sanitization, wrong sanitizer, alias sink, multi-hop flow, and false-positive regressions.

Implemented coverage includes all ten stable rule IDs, direct source-to-sink flows, assignment/alias/template/concatenation multi-hop propagation, SQL parameterization, sink-aware and wrong-sanitizer behavior, imported/default-import sink identity, unrelated same-name APIs, GraphQL variables, constants, deterministic finding IDs, and stable evidence ordering.
