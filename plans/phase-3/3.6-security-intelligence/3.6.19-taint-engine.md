# Phase 3.6.19 — Security Taint Engine

> Parent: [Security Intelligence](./README.md)

Status: ✅ Complete

## Objective
Build the shared deterministic data-flow engine used by injection, XSS, SSRF, filesystem, sensitive-data, object-security, and later banking analysis.

## Dependencies
- 3.6.0
- Existing AST/scope/declaration semantic infrastructure

## Core Model
```text
Source → Propagation → Transformation → Sanitization/Validation → Sink
```

## Deliverables
Define typed `TaintKind`, `TaintState`, `TaintSource`, `TaintSink`, `TaintSanitizer`, `TaintTransform`, `TaintPath`, and `TaintStep` models.

Initial propagation must cover assignments, aliases, template literals, concatenation, object properties, function arguments in local scope, conditional/logical expressions, destructuring where supported, and sink calls.

Use typed/multi-label taint (for example user-input, html, url, path, command, sql, secret, credential, payment-data), never a single global boolean `tainted` flag.

Sanitization is sink-aware. An HTML sanitizer cannot clear SQL/command/path taint. Unknown transformations must not magically erase taint.

Every taint-based finding should preserve source, intermediate steps, and sink as deterministic evidence.

## Determinism / Performance
Stable traversal and graph ordering are mandatory. Avoid repeated parsing/scope graph construction per rule and avoid unordered iteration affecting output.

## Tests
Assignment, alias, template, concatenation, objects/properties, destructuring, conditional/logical flow, sanitizer, wrong sanitizer, multiple sources/sinks, clean values, mixed taint, stable paths/order, and performance regressions.

## Exit Criteria
The engine is independently testable and reusable; no production rule owns a private taint implementation.
