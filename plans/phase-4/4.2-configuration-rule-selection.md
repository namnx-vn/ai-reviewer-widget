# Phase 4.2 — Configuration & Rule Selection

> Engineering contract: [`../../AGENTS.md`](../../AGENTS.md)

Status: ✅ Complete

Depends on: Phase 4.1, R1

---

## Objective

Turn the existing minimal `.ai-reviewer.json` bootstrap into a typed, validated configuration contract that can control review behavior without creating alternate analyzer pipelines.

Configuration is an application input. Deterministic analyzers, AI review, quality gates, CLI, GitHub, and future adapters must consume the same resolved configuration model.

---

## Scope

### 1. Configuration Contract

Define a versioned configuration model with explicit defaults.

Initial supported areas:

- configuration schema version
- include/exclude path patterns
- deterministic rule-family enable/disable controls
- individual rule enable/disable controls where the registry supports stable rule IDs
- severity overrides
- review profiles
- AI review mode selection through the existing provider boundary
- quality-gate/profile selection

Do not duplicate analyzer-specific configuration structures in CLI or GitHub adapters.

### 2. Configuration Loading

Introduce a configuration loader/resolver that:

- reads `.ai-reviewer.json`
- distinguishes missing configuration from invalid configuration
- applies deterministic defaults
- validates unknown/invalid values
- returns a typed resolved configuration object
- does not perform review execution itself

Filesystem access belongs to adapters. Validation and resolution should remain independently testable.

### 3. Rule Selection

Rule selection must flow through the existing analyzer contribution registry/composition path.

Requirements:

- stable rule IDs are the selection key
- disabling a rule must not unregister unrelated analyzers
- unknown rule IDs produce a clear configuration diagnostic
- ordering remains deterministic
- plugin-contributed rules follow the same selection contract when their IDs are known at composition time

### 4. Profiles

Support named review profiles without hard-coding repository-specific policy into analyzers.

Initial profile model should be small and composable, for example:

```text
default
strict
security-focused
performance-focused
```

Exact profile contents must be derived from existing rule/profile capabilities when implementation begins.

### 5. Adapter Integration

Integrate resolved configuration into:

- local CLI
- GitHub PR review
- plugin-aware review composition where applicable

All adapters must continue to call the shared application review use cases.

---

## Suggested Boundaries

```text
src/config/
  contracts.ts
  defaults.ts
  validate.ts
  resolve.ts
  index.ts

src/application/review/
  configuration port/input integration

src/cli/
  config file IO adapter only

src/github/
  repository config retrieval adapter only when needed
```

Reuse the existing `src/config/` boundary if current code already owns related configuration logic.

---

## Non-Goals

- remote organization policy management
- hosted configuration service
- database persistence
- UI configuration editor
- new state-management framework
- replacing existing security/performance profile systems without a migration plan

---

## Acceptance Criteria

- [x] `.ai-reviewer.json` has a typed, versioned contract.
- [x] Missing configuration uses explicit deterministic defaults.
- [x] Invalid configuration produces stable diagnostics and non-zero CLI failure where appropriate.
- [x] Include/exclude filtering is applied consistently across supported adapters.
- [x] Rule-family and supported rule-ID selection goes through analyzer composition, not duplicated adapter logic.
- [x] Severity/profile overrides are applied at the correct policy boundary without mutating analyzer internals ad hoc.
- [x] CLI and GitHub review resolve the same configuration semantics.
- [x] Tests cover defaults, invalid config, rule selection, profiles, path filtering, and adapter integration.
- [x] No new runtime dependency unless separately justified and approved.
- [x] `npm run typecheck`, `npm run lint`, `npm test`, and `npm run build` pass.

## Implementation Evidence

- Added typed configuration contracts, defaults, validation, path matching, and filesystem loading under `src/config/` and `src/cli/config-file.ts`.
- Analyzer composition now accepts a selection model for disabled contribution IDs, disabled rule IDs, and severity overrides while keeping ordering deterministic.
- Default and plugin review composition expose rule catalogs so unknown stable rule IDs can be rejected once contribution IDs are known.
- CLI and GitHub PR review both resolve the same configuration semantics; GitHub path selection is applied before PR file content is loaded.
- Validation performed on 2026-09-01: `npm run typecheck`, `npm run lint`, `npm test` (101 files, 730 tests), `npm run build`, and `npm run test:coverage`.
- Coverage command passed with global statements 86.54%, functions 95.44%, lines 87.65%, and branches 77.44%; branch coverage remains a repository-wide residual gap rather than a Phase 4.2 threshold failure.
