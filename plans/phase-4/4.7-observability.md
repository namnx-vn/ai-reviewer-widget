# Phase 4.7 — Observability & Operational Diagnostics

> Engineering contract: [`../../AGENTS.md`](../../AGENTS.md)

Status: ⏳ Planned

Depends on: Phase 4.5

Can progress in parallel with: Phase 4.6

---

## Objective

Make review execution explainable and operable by exposing structured timing, failure, and cost telemetry without leaking secrets or coupling core logic to a telemetry vendor.

---

## Scope

### 1. Review Run Telemetry

Capture structured metrics/events for major pipeline stages:

- source collection
- deterministic analyzer execution
- React/MFE/security/performance analyzer groups where available
- AI review latency
- merge/deduplication
- quality-gate evaluation
- publication/persistence adapters
- total run duration

### 2. AI Usage Diagnostics

Where provider responses expose usage safely, capture:

- model identifier
- request count
- latency
- token/usage metadata
- retry count
- partial specialist failures in multi-agent mode

Cost estimation must be optional and must not hard-code stale provider prices into domain logic.

### 3. Structured Diagnostics

Define stable diagnostic categories for:

- configuration failures
- parse/source failures
- analyzer failures
- AI provider failures
- publication failures
- persistence failures
- policy/quality-gate failures

Reuse existing `ReviewWarning` semantics where appropriate instead of inventing duplicate warning systems.

### 4. Telemetry Port

Expose an application-level telemetry sink/port with a no-op default.

Requirements:

- telemetry must not change review decisions
- telemetry failures must not fail analysis by default
- core/domain code must not depend on a vendor SDK
- payloads must be sanitized

### 5. Developer Diagnostics

Provide deterministic debug/diagnostic output suitable for local/CI troubleshooting without enabling noisy production logging by default.

---

## Non-Goals

- selecting Datadog, OpenTelemetry backend, Sentry, or another vendor in the plan itself
- storing source code in telemetry
- replacing existing review warnings with logs
- analytics dashboards

---

## Acceptance Criteria

- [ ] Major review stages expose structured timing/diagnostic events.
- [ ] AI usage metadata is captured only when available and safe.
- [ ] A no-op telemetry implementation keeps existing behavior unchanged.
- [ ] Telemetry failures do not silently alter review findings, scores, or decisions.
- [ ] Sensitive source/configuration values are not emitted.
- [ ] Diagnostic categories are stable and covered by tests.
- [ ] CLI/CI can expose useful diagnostics without adding debug logging to domain/analyzer code.
- [ ] `npm run typecheck`, `npm run lint`, `npm test`, and `npm run build` pass.
