## Implementation Summary

### Operational telemetry contract

The application now exposes a vendor-neutral `OperationalTelemetryPort` and stable event contracts for:

- stage timing
- structured diagnostics
- correlation metadata
- safe AI usage metadata

`NOOP_OPERATIONAL_TELEMETRY` and `recordOperationalTelemetry()` preserve existing behavior when no sink is configured or when a sink throws.

### Instrumented stages

Structured timing is emitted for:

- `source.collection`
- `configuration.resolution`
- `review.execution`
- `deterministic.analysis`
- `ai.review`
- `quality-gate.evaluation`
- `persistence.save`
- `publication.publish`
- `platform.total`

Instrumentation remains in application/platform orchestration boundaries; domain and analyzer modules do not log or depend on telemetry SDKs.

### AI usage metadata

`AIReviewResponse` may optionally expose safe usage metadata:

- model identifier
- request count
- input/output/total tokens
- retry count
- partial failure count

No provider pricing is hard-coded and cost estimation remains outside domain logic.

### Stable diagnostics

Operational categories are explicit and typed:

- configuration
- source
- analyzer
- AI provider
- publication
- persistence
- quality gate
- platform

Existing `ReviewWarning` codes are mapped into these categories rather than replaced by a duplicate warning model. Adapter-stage failures also emit their specific categories, including persistence and publication failures.

### Data minimization

Telemetry payloads contain stage names, codes, timing, correlation IDs, and explicitly supplied usage metadata only. Raw source content, diffs, configuration values, review titles/descriptions, and secret-bearing error payloads are not part of the operational event contract.

### Failure isolation

Telemetry is best-effort by default. A telemetry sink failure is swallowed by the application telemetry helper and does not change findings, score, decision, warnings, or adapter success/failure semantics.

---

## Non-Goals

- selecting Datadog, OpenTelemetry backend, Sentry, or another vendor
- storing source code in telemetry
- replacing existing review warnings with logs
- analytics dashboards
- hard-coded model pricing

---

## Acceptance Criteria

- [x] Major review stages expose structured timing/diagnostic events.
- [x] AI usage metadata is captured only when available and safe.
- [x] A no-op telemetry implementation keeps existing behavior unchanged.
- [x] Telemetry failures do not silently alter review findings, scores, or decisions.
- [x] Sensitive source/configuration values are not emitted.
- [x] Diagnostic categories are stable and covered by tests.
- [x] CLI/CI can consume deterministic developer diagnostics without adding debug logging to domain/analyzer code.
- [x] `npm run typecheck`, `npm run lint`, `npm test`, and `npm run build` pass.
