## Implementation Summary

### Typed and versioned organization policy

`OrganizationPolicyV1` defines organization governance for:

- default review profile
- required rule families
- rules that repositories may not disable
- minimum rule severities
- mandatory security quality-gate policy
- allowed AI modes/providers
- repository and invocation override permissions
- explicit policy ID/version

Provider-specific organization identity remains opaque application metadata; GitHub installation/account mapping is not introduced into policy models.

### Deterministic precedence and provenance

`resolveOrganizationPolicy()` resolves effective configuration in the explicit order:

```text
built-in resolved configuration
  ↓
organization defaults
  ↓
allowed repository configuration
  ↓
allowed invocation overrides
  ↓
mandatory organization constraints
```

The returned `EffectivePolicyContextV1` records organization ID, policy ID/version, the final resolved review configuration, and typed provenance entries explaining which layer supplied or enforced important values.

### Repository override governance

Repository configuration does not receive implicit permission to override organization policy. Policy permissions explicitly control changes to:

- profile
- disabled rule families
- disabled individual rules
- severity overrides
- AI mode
- AI provider
- security quality-gate profile

Forbidden repository and invocation overrides fail explicitly with `GOVERNANCE_OVERRIDE_FORBIDDEN` rather than being silently ignored.

### Mandatory controls

Organization constraints are evaluated independently of override permissions and cannot be silently weakened:

- required rule families cannot be disabled
- protected rules cannot be disabled
- configured severities cannot be below organization minimums
- AI mode/provider must remain within the organization allow-list
- mandatory security quality gates cannot be weaker than the configured minimum profile

Stable `GovernancePolicyErrorCode` values make rejected governance decisions auditable and deterministic.

### Existing pipeline integration

`createGovernedPlatformReviewService()` loads organization policy, resolves the effective configuration, and then delegates directly to the existing `PlatformReviewService`.

No organization-specific analyzer, scoring path, AI orchestration, or quality-gate implementation was introduced.

### Historical policy context

Review-run snapshots can now retain a compact persisted policy context containing:

- organization ID
- policy ID
- policy version
- provenance entries

The effective review configuration remains stored in the existing `configuration` snapshot field, avoiding duplicate configuration storage while preserving enough context to explain historical reviews after organization policy changes.

## Non-Goals

- billing/subscriptions
- full RBAC implementation
- GitHub Marketplace installation UX
- organization dashboard UI
- multi-tenant database vendor selection
- enterprise SSO

## Acceptance Criteria

- [x] Organization and repository policy contracts are typed/versioned.
- [x] Policy precedence is deterministic and independently testable.
- [x] Effective configuration includes provenance for important policy decisions.
- [x] Mandatory organization gates cannot be silently weakened by repository config.
- [x] Provider-specific organization/repository identity stays in adapters/application metadata.
- [x] Review runs retain the effective policy/configuration snapshot needed for historical explanation.
- [x] Organization policy feeds the existing application review pipeline rather than creating a new one.
- [x] Tests cover precedence, forbidden overrides, repository policy resolution, provenance, and history integration.
