# Phase 4.4 — CI Adapters & Portable Review Output

> Engineering contract: [`../../AGENTS.md`](../../AGENTS.md)

Status: ✅ Complete

Depends on: Phase 4.2, Phase 4.3

---

## Objective

Make the reviewer easy to run in continuous integration without embedding CI-provider behavior inside the review engine.

---

## Scope

### 1. Portable CI Contract

Define a process-independent CI result contract containing:

- review decision
- score and summary statistics
- findings
- warnings
- quality-gate result
- stable exit classification
- optional machine-readable metadata needed by adapters

The contract must be derived from application/domain results rather than reconstructed from terminal output.

### 2. GitHub Actions Integration

Provide a reusable GitHub Actions execution path that can invoke the distributable CLI or shared application adapter.

Requirements:

- repository checkout remains external to the review engine
- configuration comes from the Phase 4.2 contract
- review result determines action success/failure predictably
- annotations/check output reuse existing GitHub publication behavior where appropriate
- avoid creating a second GitHub review pipeline

### 3. Machine-Readable Formats

Support automation-friendly output.

Target formats:

- JSON as the canonical portable format
- SARIF where findings can be represented faithfully

Formatters must not alter review decisions or finding semantics.

### 4. CI Environment Abstraction

If environment detection is required, keep it in a dedicated adapter layer.

Do not add provider conditionals to `domain/`, analyzers, or core application use cases.

### 5. Artifact and Summary Output

Allow CI integrations to publish:

- review summary
- JSON result artifact
- optional SARIF artifact/upload input

Publication failures should be distinguishable from analysis failures.

---

## Non-Goals

- hosted control plane
- organization policy synchronization
- persistence/history service
- CI providers beyond explicitly implemented adapters
- changing analyzer findings to fit SARIF limitations

---

## Acceptance Criteria

- [x] CI execution uses the same application review pipeline as CLI and GitHub review.
- [x] JSON result schema is stable/versioned.
- [x] SARIF conversion is isolated from domain/analyzer logic.
- [x] GitHub Actions failure behavior matches review decisions and documented exit codes.
- [x] Analysis failures and publication/integration failures remain distinguishable.
- [x] Tests cover conversion, exit behavior, and adapter orchestration.
- [x] No duplicate review pipeline is introduced.
- [x] `npm run typecheck`, `npm run lint`, `npm test`, and `npm run build` pass.

## Implementation Evidence

- Added a process-independent, versioned CI execution contract derived from `ReviewResult`, with stable `success`, `review_failed`, `analysis_failed`, and `publication_failed` classifications mapped to exit codes `0`, `1`, and `2`.
- CLI JSON now delegates to the canonical portable review formatter; CI artifact generation adds JSON, SARIF 2.1.0, and Markdown summary outputs without changing finding or decision semantics.
- SARIF conversion is isolated under `src/ci/`, deduplicates rule metadata, normalizes safe repository-relative URIs, and converts source columns to valid one-based SARIF positions.
- GitHub PR analysis and publication are separate stages while `reviewGitHubPullRequest()` remains the compatibility wrapper over the shared application pipeline.
- The GitHub Actions process adapter sanitizes operational failures, retains completed review data when publication fails, emits fixed output keys, and uploads artifacts without obscuring earlier workflow failures.
- Validation performed on 2026-09-02: `npm run typecheck`, `npm run lint`, `npm test` (115 files, 776 tests), `npm run build`, `npm run test:coverage`, `npm run security:secrets`, and focused CI/GitHub suites.
- Global coverage passed configured thresholds at 86.58% statements, 77.56% branches, 95.40% functions, and 87.67% lines; `src/ci` reached 100% statements/functions/lines and 97.10% branches.
