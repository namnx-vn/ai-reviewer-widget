# Phase 4.5 — Platform API Boundary

> Engineering contract: [`../../AGENTS.md`](../../AGENTS.md)

Status: ✅ Complete

Depends on: Phase 4.2

---

## Objective

Define a transport-neutral platform API boundary so future HTTP, worker, desktop, or hosted adapters can invoke the reviewer without importing CLI/GitHub infrastructure or duplicating orchestration.

---

## Scope

### 1. Application Request/Response Contracts

Define explicit request/result contracts for platform execution, including:

- source/repository identity metadata
- source files or repository source-provider reference
- resolved review configuration
- review mode/options
- correlation/run metadata
- `ReviewResult`-derived response

These contracts belong at the application/platform boundary and must remain independent of HTTP frameworks.

### 2. Review Service Facade

Introduce a small application-facing facade that coordinates existing review use cases.

Requirements:

- delegates to `src/application/review`
- does not duplicate deterministic/AI sequencing
- receives infrastructure through ports/dependencies
- is independently testable without network/process IO

### 3. Adapter Ports

Define only ports that are required for platform execution, such as:

- source/repository retrieval
- configuration retrieval
- review-result publication
- run persistence hook
- telemetry hook

Do not select concrete hosted infrastructure in this phase.

### 4. API Versioning

Establish a versioning strategy for externally consumed request/result contracts.

Breaking changes must be explicit and must not silently alter existing CLI/GitHub behavior.

### 5. Security Boundary

The platform boundary must not trust caller-provided paths, provider configuration, or AI endpoints implicitly.

Reuse existing input-policy/security controls rather than bypassing them.

---

## Implemented Structure

```text
src/application/platform/
  contracts.ts
  ports.ts
  review-service.ts
  index.ts
  __tests__/
    review-service.test.ts
```

Implementation notes:

- `PlatformReviewRequestV1` and `PlatformReviewResponseV1` make the initial external contract explicit and preserve a clean future V2 migration path.
- `createPlatformReviewService()` delegates file and pull-request execution to the existing `ReviewUseCases` boundary.
- Inline and referenced source inputs share one platform request model.
- Repository source, configuration, publication, persistence, and telemetry capabilities are injected through ports.
- Caller-controlled source paths are rejected when absolute, traversal-based, empty, or otherwise unsafe for repository-relative execution.
- AI provider selection remains an injected application dependency; the platform request does not accept arbitrary AI endpoint configuration.
- No HTTP framework, database, auth provider, or hosted runtime was introduced.

## CI Baseline Hardening

Phase validation exposed two pre-existing CI issues:

1. the repository default branch is `develop`, while CI push validation only targeted `main`;
2. the repository currently has no committed npm lockfile, while CI used npm cache + `npm ci`/`npm audit` paths that require one.

The CI workflow now validates pushes to both `main` and `develop` and generates an ephemeral npm lockfile with `npm install` so the existing audit/SBOM/quality gates execute successfully. This does not change runtime application behavior.

## Non-Goals

- choosing Express/Fastify/Nest/Next.js or another server framework
- database implementation
- authentication/authorization implementation
- hosted deployment
- organization tenancy

---

## Acceptance Criteria

- [x] Platform request/result contracts are explicit, typed, and versionable.
- [x] Platform review execution delegates to existing application review use cases.
- [x] No concrete network/framework dependency is required.
- [x] Infrastructure concerns are represented as injected ports.
- [x] Existing CLI and GitHub execution remain behaviorally unchanged.
- [x] Tests cover request mapping, orchestration, dependency injection, and failure propagation.
- [x] Domain/analyzer layers do not import platform adapters.
- [x] `npm run typecheck`, `npm run lint`, `npm test`, and `npm run build` pass through CI validation.
