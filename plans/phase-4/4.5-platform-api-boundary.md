# Phase 4.5 — Platform API Boundary

> Engineering contract: [`../../AGENTS.md`](../../AGENTS.md)

Status: ⏳ Planned

Depends on: Phase 4.2

---

## Objective

Define a transport-neutral platform API boundary so future HTTP, worker, desktop, or hosted adapters can invoke the reviewer without importing CLI/GitHub infrastructure or duplicating orchestration.

---

## Scope

### 1. Application Request/Response Contracts

Define explicit request/result contracts for platform execution, including:

- source/repository identity metadata
- source files or repository source-provider reference
- resolved review configuration
- review mode/options
- correlation/run metadata
- `ReviewResult`-derived response

These contracts belong at the application/platform boundary and must remain independent of HTTP frameworks.

### 2. Review Service Facade

Introduce a small application-facing facade that coordinates existing review use cases.

Requirements:

- delegates to `src/application/review`
- does not duplicate deterministic/AI sequencing
- receives infrastructure through ports/dependencies
- is independently testable without network/process IO

### 3. Adapter Ports

Define only ports that are required for platform execution, such as:

- source/repository retrieval
- configuration retrieval
- review-result publication
- run persistence hook
- telemetry hook

Do not select concrete hosted infrastructure in this phase.

### 4. API Versioning

Establish a versioning strategy for externally consumed request/result contracts.

Breaking changes must be explicit and must not silently alter existing CLI/GitHub behavior.

### 5. Security Boundary

The platform boundary must not trust caller-provided paths, provider configuration, or AI endpoints implicitly.

Reuse existing input-policy/security controls rather than bypassing them.

---

## Suggested Structure

```text
src/application/platform/
  contracts.ts
  ports.ts
  review-service.ts
  index.ts
```

A concrete HTTP server/framework is intentionally out of scope until separately approved.

---

## Non-Goals

- choosing Express/Fastify/Nest/Next.js or another server framework
- database implementation
- authentication/authorization implementation
- hosted deployment
- organization tenancy

---

## Acceptance Criteria

- [ ] Platform request/result contracts are explicit, typed, and versionable.
- [ ] Platform review execution delegates to existing application review use cases.
- [ ] No concrete network/framework dependency is required.
- [ ] Infrastructure concerns are represented as injected ports.
- [ ] Existing CLI and GitHub execution remain behaviorally unchanged.
- [ ] Tests cover request mapping, orchestration, dependency injection, and failure propagation.
- [ ] Domain/analyzer layers do not import platform adapters.
- [ ] `npm run typecheck`, `npm run lint`, `npm test`, and `npm run build` pass.
