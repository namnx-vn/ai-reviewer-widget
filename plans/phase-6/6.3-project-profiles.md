# Phase 6.3 — Project Profiles & Environment Detection

Status: ✅ Complete

## Objective

Adapt review behavior to the real project type without creating separate review pipelines.

## Initial Profiles

- `typescript-library`
- `react-application`
- `node-service`
- `nextjs-application`
- `micro-frontend`
- `monorepo`
- `security-sensitive`
- `performance-sensitive`

Profiles may compose deterministically.

## Detection Signals

Use repository context signals such as:

- `package.json` dependencies/devDependencies
- workspace configuration
- `tsconfig.json`
- known framework config files
- source/import patterns
- package boundaries

Explicit configuration must override automatic detection.

## Configuration Direction

Extend the existing versioned configuration system rather than introduce another config path.

```json
{
  "profile": ["react-application", "security-sensitive"]
}
```

Automatic mode may be supported as:

```json
{
  "profile": "auto"
}
```

## Constraints

- No analyzer should independently read `package.json`.
- Profile resolution must remain explainable and deterministic.
- Unknown frameworks must safely fall back to general behavior.
- Profiles alter existing configuration/rule selection; they do not own separate analyzers.

## Acceptance Criteria

- [x] versioned project-profile contract exists
- [x] supported profiles compose deterministically
- [x] auto-detection exposes evidence/reasoning signals
- [x] explicit configuration overrides detection
- [x] profile selection flows through existing config resolution
- [x] unknown project types do not crash review
- [x] profile conflicts have deterministic precedence
- [x] monorepo package profiles are covered
- [x] explicit-vs-auto behavior is tested
- [x] no duplicate configuration system is introduced

## Implementation Notes

- `src/config/project-profiles.ts` owns the versioned profile vocabulary, evidence contract, precedence, and deterministic detector.
- The existing `profile` field remains backward compatible with legacy review presets; it additionally accepts `"auto"` or an explicit array of project profiles.
- `resolveReviewConfiguration` is still the single configuration resolution path and accepts optional repository-derived profile signals.
- Explicit project profiles ignore auto-detection signals; explicit rule and quality-gate configuration continues to override profile-derived defaults.
- Security-sensitive and performance-sensitive profiles reuse existing security-quality-gate and severity capabilities instead of creating new analyzers.
- Monorepo, Next.js/React composition, unknown-framework fallback, explainable evidence, and explicit-vs-auto behavior are covered by tests.
- Completion was validated by GitHub Actions with typecheck, lint, evaluation smoke tests, full tests/coverage, build, and e2e all passing.
