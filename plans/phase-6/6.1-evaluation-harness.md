# Phase 6.1 — Real-World Evaluation Harness

Status: ✅ Complete

## Objective

Create an objective, reproducible way to measure reviewer quality and detect regressions before expanding more intelligence.

## Scope

- Versioned evaluation-case contracts.
- Controlled real-world-style repository fixtures.
- Expected finding manifests.
- Deterministic finding matcher.
- Precision, recall, false-positive, false-negative, severity, duplicate, stability, and runtime metrics.
- Human-readable and JSON reports.
- CI smoke corpus.

## Proposed Structure

```text
src/evaluation/
├── contracts.ts
├── runner.ts
├── matcher.ts
├── metrics.ts
├── report.ts
├── real-world.ts
├── real-world-catalog.ts
├── real-world-observation.ts
├── real-world-promoted-security*.ts
├── real-world-promoted-react*.ts
├── real-world-promoted-clean*.ts
├── index.ts
└── __tests__/

evaluation/
├── fixtures/
│   ├── smoke/
│   └── real-world/
├── real-world/
├── manifests/
└── baselines/
```

Initial fixture categories: React application, enterprise React, Node service, TypeScript library, monorepo, security-sensitive, performance-sensitive, Next.js-style, and micro-frontend.

## Constraints

- Evaluation must call the production application review pipeline rather than duplicate it.
- Fixtures must not contain real secrets or proprietary source.
- Metrics must be deterministic for deterministic findings.
- Large public repositories should not become ordinary unit-test dependencies.

## Acceptance Criteria

- [x] versioned evaluation-case contract exists
- [x] expected findings can be matched deterministically
- [x] precision and recall are calculated
- [x] false positives and false negatives are explicit
- [x] severity accuracy and duplicate rate can be reported
- [x] runtime is recorded
- [x] repeated runs can measure finding stability
- [x] JSON report output exists
- [x] CI runs a deterministic smoke corpus
- [x] matcher and metric calculations have unit tests
- [x] production review orchestration is not duplicated
- [x] existing validation remains green

## Implementation Notes

- `src/evaluation/` contains the versioned contracts, matcher, metrics, reports, observation report, and suite runner.
- The runner accepts the existing `ReviewUseCases` application boundary and calls `reviewFiles`, preserving the production orchestration path.
- `evaluation/fixtures/smoke/basic.ts` provides the deterministic CI smoke fixture.
- `npm run test:evaluation` runs evaluation tests in CI before the full test/build gates.
- `npm run evaluation:real-world-report` publishes an offline observation artifact from the executable public-PR corpus.

### Post-completion real-world hardening

The evaluation harness has two complementary public-PR layers:

1. `src/evaluation/real-world-catalog.ts` is a fixed 100-PR selection and human-classification backlog.
2. `src/evaluation/real-world.ts` plus `evaluation/fixtures/real-world/` contains minimized executable regression cases that run offline through the production review pipeline.

The 100-PR catalog remains quota-balanced:

- 20 security PRs
- 15 React/hooks/reactive-lifecycle PRs
- 20 performance PRs
- 30 Next.js/RSC PRs
- 15 clean negative controls

Catalog signals remain conservative: `positive-candidate`, `negative-control`, and `manual-review`. Human adjudication may change a catalog signal before promotion when the actual diff contradicts the initial metadata classification.

#### Batch 1 executable promotion

Batch 1 expanded the executable corpus from 3 to 30 manually reviewed public PR cases. It also exposed the first useful empirical false-positive cluster: runtime lifecycle performance rules were firing on upstream test helpers. The fix was applied at the performance engine policy boundary rather than inside individual rules, and the original three empirical test controls moved from 2/3 noisy cases to 0/3 on the same fixtures.

#### Batch 2 executable promotion

Batch 2 expands the executable corpus from 30 to **50 manually reviewed public PR cases**:

- 20 security/trust-boundary cases
- 15 React/hooks/reactive-lifecycle cases
- 1 performance negative control
- 14 clean false-positive controls

The 50 cases carry **53 human expectations**:

- 17 `must-find`
- 31 `must-not-find`
- 5 `advisory`

All 20 security catalog entries and all 15 React/hooks catalog entries are now executable. Four additional clean controls are promoted; `vercel/next.js#97284` deliberately remains catalogued because its relevant implementation is Rust-only and the current executable harness is TypeScript/TSX.

Two Batch-2 test-only Vue Query PRs retain their upstream-like `__tests__/*.test.ts` paths and join the empirical negative-control set. Observation schema v3 reports aggregate empirical negative-control false-positive pressure across those five cases while retaining clean-only metrics for historical comparison.

Promoted cases preserve repository, PR number, canonical URL, exact head SHA, human expectation, and catalog `fixtureId` linkage. Fixture bundles fail closed on invalid shape, missing key, or empty content. Replays continue to call the shared `ReviewUseCases.reviewFiles` production path.

#### Human-adjudication corrections

`TanStack/query#11380` was removed from the clean negative-control set after manual verification showed that its Preact SSR guide introduced the raw `JSON.stringify(...)`-inside-`<script>` example later fixed by `#11381` as XSS-unsafe. It was replaced by merged test-only `TanStack/query#11258`.

`vercel/next.js#97284` remains catalogued rather than minimized because the current TS/TSX runner cannot faithfully execute its Rust-only backend-storage refactor. A TypeScript stand-in would weaken corpus validity, so the Batch-2 clean slot is filled by `TanStack/query#11378` instead.

These corrections demonstrate why catalog membership alone is not quality evidence: labels become trustworthy only after reviewing the relevant diff and promoting a faithful minimized reproduction.

Fifty executable PRs are sufficient to begin a more useful empirical baseline. They are **not sufficient to claim the documented 90% high-severity real-world precision target**. The next step is to map human `must-find` expectations to exact production rule IDs observed in the 50-case report, calculate recall only on the mapped subset, and continue expanding toward several hundred adjudicated findings across representative production repositories before empirical precision becomes a blocking release criterion.
