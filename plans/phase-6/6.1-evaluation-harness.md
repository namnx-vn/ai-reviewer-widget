# Phase 6.1 — Real-World Evaluation Harness

Status: ✅ Complete

## Objective

Create an objective, reproducible way to measure reviewer quality and detect regressions before expanding more intelligence.

## Scope

- Versioned evaluation-case contracts.
- Controlled real-world-style repository fixtures.
- Expected finding manifests.
- Deterministic finding matcher.
- Precision, recall, false-positive, false-negative, severity, duplicate, stability, and runtime metrics.
- Human-readable and JSON reports.
- CI smoke corpus.

## Proposed Structure

```text
src/evaluation/
├── contracts.ts
├── runner.ts
├── matcher.ts
├── metrics.ts
├── report.ts
├── real-world.ts
├── real-world-catalog.ts
├── real-world-promoted-security.ts
├── real-world-promoted-react.ts
├── real-world-promoted-clean.ts
├── index.ts
└── __tests__/

evaluation/
├── fixtures/
│   ├── smoke/
│   └── real-world/
├── real-world/
├── manifests/
└── baselines/
```

Initial fixture categories: React application, enterprise React, Node service, TypeScript library, monorepo, security-sensitive, performance-sensitive, Next.js-style, and micro-frontend.

## Constraints

- Evaluation must call the production application review pipeline rather than duplicate it.
- Fixtures must not contain real secrets or proprietary source.
- Metrics must be deterministic for deterministic findings.
- Large public repositories should not become ordinary unit-test dependencies.

## Acceptance Criteria

- [x] versioned evaluation-case contract exists
- [x] expected findings can be matched deterministically
- [x] precision and recall are calculated
- [x] false positives and false negatives are explicit
- [x] severity accuracy and duplicate rate can be reported
- [x] runtime is recorded
- [x] repeated runs can measure finding stability

- [x] matcher and metric calculations have unit tests
- [x] production review orchestration is not duplicated
- [x] existing validation remains green

## Implementation Notes

- `src/evaluation/` contains the versioned contracts, matcher, metrics, reports, and suite runner.
- The runner accepts the existing `ReviewUseCases` application boundary and calls `reviewFiles`, preserving the production orchestration path.
- `evaluation/fixtures/smoke/basic.ts` provides the initial deterministic CI smoke fixture.
- `npm run test:evaluation` runs the smoke corpus in CI before the full test/build gates.
- Completion was validated by GitHub Actions with typecheck, lint, evaluation smoke tests, full tests/coverage, build, and e2e all passing.

### Post-completion real-world hardening

The evaluation harness has two complementary public-PR layers:

1. `src/evaluation/real-world-catalog.ts` is a fixed 100-PR selection and human-classification backlog.
2. `src/evaluation/real-world.ts` plus `evaluation/fixtures/real-world/` contains minimized executable regression cases that run offline through the production review pipeline.

The 100-PR catalog remains quota-balanced:

- 20 security PRs
- 15 React/hooks/reactive-lifecycle PRs
- 20 performance PRs
- 30 Next.js/RSC PRs
- 15 clean negative controls

Catalog signals remain conservative: `positive-candidate`, `negative-control`, and `manual-review`. Human adjudication may change a catalog signal before promotion when the actual diff contradicts the initial metadata classification.

#### Batch 1 executable promotion

The executable corpus has been expanded from 3 to **30 manually reviewed public PR cases**:

- 12 security/trust-boundary cases, including the original two security seeds
- 7 React/hooks/reactive-lifecycle cases
- 1 performance negative control
- 10 clean false-positive controls

The 30 cases carry **32 human expectations**:

- 11 `must-find`
- 18 `must-not-find`
- 3 `advisory`

Promoted cases preserve repository, PR number, canonical URL, exact head SHA, human expectation, and catalog `fixtureId` linkage. The 27 Batch-1 snippets are stored in three small JSON bundles and loaded as case-specific virtual `.ts`/`.tsx` files. Bundle parsing fails closed on invalid shape, missing key, or empty content.

The corpus still calls the shared `ReviewUseCases.reviewFiles` production path for every deterministic replay. `src/evaluation/__tests__/real-world.test.ts` validates 30-case provenance, expectation counts, fixture loading, and repeated deterministic output. `src/evaluation/__tests__/real-world-catalog.test.ts` validates 100 unique catalog entries, fixed category quotas, 30 minimized mappings, and human-adjudication regressions.

#### Human-adjudication correction

`TanStack/query#11380` was removed from the clean negative-control set after manual verification showed that the Preact SSR guide introduced the raw `JSON.stringify(...)`-inside-`<script>` example later fixed by `#11381` as XSS-unsafe. The clean slot was replaced by merged test-only `TanStack/query#11258`, and the catalog test now prevents `#11380` from returning as a clean control.

This correction demonstrates why catalog membership alone is not quality evidence: labels become trustworthy only after reviewing the relevant diff and promoting a minimized reproduction.

Thirty executable PRs are sufficient to start a first empirical baseline and identify obvious false-positive clusters. They are **not sufficient to claim the documented 90% high-severity real-world precision target**. The next corpus milestone is 50+ executable public PRs, followed by several hundred adjudicated findings across representative production repositories before empirical precision becomes a blocking release criterion.
