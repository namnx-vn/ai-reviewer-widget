# Phase 6.9 — Developer Feedback Loop

Status: ⏳ Planned

## Objective

Capture real developer outcomes to measure reviewer usefulness without introducing uncontrolled self-learning or automatic rule mutation.

## Feedback Types

- `accepted`
- `fixed`
- `false-positive`
- `ignored`
- `accepted-risk`
- `duplicate`
- `not-actionable`

## Feedback Contract

Feedback should reference:

- stable finding fingerprint
- rule ID
- repository/review identity
- developer action
- optional reason
- timestamp

Raw source code should not be required for ordinary feedback records.

## Uses

Feedback may inform:

- evaluation corpus curation
- false-positive analysis
- rule/profile tuning
- severity calibration
- AI prompt evaluation

Feedback must not automatically rewrite rules, prompts, severities, profiles, or governance policy.

## Architecture

Feedback persistence belongs behind an application port and may initially use a simple adapter consistent with existing persistence architecture.

## Acceptance Criteria

- [ ] feedback contract is versioned
- [ ] feedback links to stable finding identity
- [ ] storage is behind an application port
- [ ] basic feedback requires no raw source storage
- [ ] false-positive records can feed/export evaluation data
- [ ] feedback cannot silently disable mandatory governance rules
- [ ] feedback counts/quality metrics are observable
- [ ] historical and deleted findings are handled explicitly
- [ ] tests cover invalid/stale finding references
- [ ] no automatic production behavior mutation is introduced
