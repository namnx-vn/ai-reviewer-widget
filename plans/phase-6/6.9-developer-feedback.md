# Phase 6.9 — Developer Feedback Loop

Status: ✅ Complete

## Objective

Capture real developer outcomes to measure reviewer usefulness without introducing uncontrolled self-learning or automatic rule mutation.

## Feedback Types

- `accepted`
- `fixed`
- `false-positive`
- `ignored`
- `accepted-risk`
- `duplicate`
- `not-actionable`

## Feedback Contract

Feedback references:

- stable finding fingerprint
- rule ID
- repository/review identity
- developer action
- optional reason
- timestamp

Raw source code is not required for ordinary feedback records.

## Uses

Feedback may inform:

- evaluation corpus curation
- false-positive analysis
- rule/profile tuning
- severity calibration
- AI prompt evaluation

Feedback does not automatically rewrite rules, prompts, severities, profiles, or governance policy.

## Architecture

Feedback persistence lives behind an application port and initially uses a minimal in-memory adapter consistent with the Phase 4.6 persistence architecture.

## Acceptance Criteria

- [x] feedback contract is versioned
- [x] feedback links to stable finding identity
- [x] storage is behind an application port
- [x] basic feedback requires no raw source storage
- [x] false-positive records can feed/export evaluation data
- [x] feedback cannot silently disable mandatory governance rules
- [x] feedback counts/quality metrics are observable
- [x] historical and deleted findings are handled explicitly
- [x] tests cover invalid/stale finding references
- [x] no automatic production behavior mutation is introduced

## Implementation Notes

- `src/application/feedback/contracts.ts` defines the versioned v1 record, supported actions, explicit current/historical/deleted finding state, queries, metrics, and false-positive export contract.
- `DeveloperFeedbackPersistencePort` keeps storage behind the application boundary; the initial in-memory adapter clones records and provides deterministic queries.
- `createDeveloperFeedbackService()` validates `reviewRunId` against existing Phase 4.6 review history and recomputes the Phase 6.5 `fingerprintReviewFinding()` identity from the stored finding instead of trusting client-provided identity blindly.
- Unknown review runs, repository mismatches, rule mismatches, and invalid finding fingerprints fail closed with `InvalidDeveloperFeedbackError`.
- Ordinary feedback and false-positive exports contain metadata only and require no raw source code.
- Aggregate metrics expose total counts, per-action counts, false-positive rate, and actionable rate for evaluation/reporting.
- Feedback APIs contain no rule/profile/severity/governance mutation capability; tests verify feedback does not alter historical review output.
